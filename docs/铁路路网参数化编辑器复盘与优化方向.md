# 铁路路网参数化编辑器：现状复盘与优化方向

- 评审日期: 2026-10-29
- 评审对象: 铁路轨道 (`track_geojson.go` / `track_yard.go` / `yard_layout.go`)、接触网 (`ocs_anchor.go` / `ocs_layout.go` / `anchor_geojson.go` / `ocs_joint.go` / `ocs_support.go` / `ocs_switch_mast.go`)、装配与配方 (`assembly.go` / `assembly_parametric.go`) 及其 C++ 图元

## ⭐ 方向修订 (2026-10-29 评审当日, 已开始落地)

评审发布后确认了两条关键决策, 修订本文的部分建议:

### 修订一: 持久化格式 = GeoJSON + 生成参数, 不是结构化派生模型

编辑器保存的是**最基础的点线 + 参数** (线路中心线 GeoJSON + 各专业生成参数,
即 flywave-topovis `model.TopoData` 的既有形态: `geometry`=GeoJSON,
`topology`/`properties`=参数)。本文 §5.1 附录 B 的 `Project` 结构化模型
**不作为持久化格式** — 那仍然是一种"算法产物落盘"。

由此推论:

- 布局 (`YardLayout` / `AnchorSectionLayout`) 是生成规则的**内存产物**, 不落盘;
  "派生字段不持久化"自动成立, 不需要再做字段级标注/裁剪;
- 算法升级 = 用新规则重跑同一份 GeoJSON+参数, **没有数据迁移问题**;
- §3.1/§3.2 指出的"快照式布局"问题从格式上消除: 编辑语义 = 改输入参数
  (含人工覆盖), 重建 = 重跑规则 → 确定性 builder;
- 人工覆盖 (overrides) 是参数的一部分 (如"该道岔号数=9"), 仍是保存对象。

### 修订二: 组装算法上移 flywave-topovis, 作为生成规则

**结论: 应当上移。** go-topo 保留几何内核职责, "识别/布柱/弛度"等组装算法
是业务规则, 落在 `flywave-topovis/railway/rules` (已落地):

| 层 | 职责 | 现状 |
|----|------|------|
| go-topo | 几何原子 (primitives) + **确定性 builder** (layout→装配) + 配方往返 (`RebuildFromParametric`) | ✅ 定稿: 识别/布柱等组装内容 (`ComputeYardLayout`/`ComputeAnchorSectionLayout`/`CalcOcsSpanPositions`/GeoJSON 组合入口) 已**彻底删除** — go-topo 只剩"显式输入→几何"的参数化内容 |
| flywave-topovis `railway/rules` | 拓扑抽取 (端点聚类/T 型吸附打断/节点分类/网格索引交叉检测) + 参数建议 (道岔号数/开向/导曲线半径实测拟合/布柱/弛度) + 结构化结论 (Junction 原因码 / Issue 报告) | ✅ 已落地, 站场与锚段规则与 go-topo 对拍一致 (≤1mm), 规则测试无 cgo |
| flywave-topovis `railway` | 生成门面 (`GenerateYardAssembly` / `GenerateAnchorSectionAssembly`: GeoJSON+参数 → rules → go-topo builder) + 既有 builder 分发/配方闭环 | ✅ 门面已落地 |

上移理由:

1. go-topo 是 cgo/OCCT 内核, 规则迭代不应绑定内核发版; 规则是纯平面折线
   数学, 无 OCCT 依赖, 上移后规则测试脱离 cgo (ms 级 vs 秒级);
2. 持久化=原始输入后, 规则是"输入→几何"的唯一变换, 天然属于 builder 分发层
   (topovis) 而非几何库;
3. 未来浏览器侧预览: 纯 Go 规则可比整库更轻地编译 wasm (不链接 OCCT);
4. 迁移有安全网: go-topo 既有 69/69 验收的实现作为对拍基准
   (`railway/generate_test.go`)。

本文其余章节的问题清单与能力缺口 (§3.3 算法覆盖、§4 P0-P2、§5.4 算法补齐、
§5.5 校验) **仍然有效**, 只是承载位置从 go-topo 改为 rules 层:

- P0-3 (T 型吸附/打断/节点分类) → `rules/extract.go` ✅ 已实现;
- P1-5 (交叉识别 O(E²·N²)) → `rules/extract.go` 均匀网格索引 ✅ 已实现;

  已实现 (替代静默跳过);
- P0-5 (结构化校验) → `rules/issue.go` + 各规则输出 Issues, 发布接口在平台侧
  组合;
- **可视化验收体系同步迁移** (2026-10-29): go-topo 定位为底层参数化库,

  §6 路线推进, 全部落在 rules 层。

## 0. 结论摘要

**方向是对的，粒度是对的，但当前产物是"算法快照"而不是"可编辑的路网模型"。**

已经具备的能力（且有回归/验收证据）：

1. **三级确定性重建**：布局 JSON（`YardLayout` / `AnchorSectionLayout`）→ 装配层级 → 每个节点挂配方 → `ExportParametric` / `RebuildFromParametric` 往返。实测 bbox 差 ≤1mm，导出再导出逐字节等价。
2. **专业层级与编辑粒度对齐**：`yard → track/turnout/crossing`、`anchor_section → mast/span`，零件级不进入地图对象列表。
3. **真实尺寸与视觉验收**：69 项铁路用例全通过（`acceptance/report.md`），覆盖钢轨/道岔/菱形/锚段/关节/支柱角色。
4. **单站场、单锚段、近直线主线的自动识别**可用：端点三叉 → 单开道岔，边中部相交 → 菱形交叉，道岔号数/开向/导曲线半径由几何实测拟合。

距离"路网编辑器"目标的三类硬差距：

| 差距 | 性质 | 影响 |
|------|------|------|
| 没有"项目/路网/线路"层，也没有稳定 ID | 数据模型 | 多站场、区间、多锚段无法组织；前端删改一个对象后所有索引失效；算法重算会覆盖手工调整 |
| 布局里派生数据与输入数据混存，部分导出字段在重建时被忽略 | 数据模型 | "保存后还原"能还原**生成结果**，但"继续编辑并保持一致"只部分成立；数据体积约为必要量的 3 倍 |
| 组装算法只覆盖"教科书站场"形态 | 算法 | 曲线主线不出岔、无 T 型顺接、无四叉/交叉渡线/复式交分、站场多股道接触网（软/硬横跨）没有布局生成器、道岔硬编码 1435/60kg、站场股道无道床 |

另外三项工程性缺口：

- **没有运行时校验/发布接口**：现有验证只在测试与验收脚本里；`Warnings` 是中文自由文本，前端无法消费。
- **规模不可用**：菱形交叉识别是 `O(E²·N²)`；整网重算全量三角化；布局 JSON 重复存中心线。
- **竖向基准不统一**：同一条 GeoJSON 喂给轨道与接触网，接触线实际导高比参数少 376mm（枕高 200 + 轨高 176）。

建议的推进顺序：**先立数据模型（真源 + ID + 版本）**，再补拓扑抽取与曲线道岔，然后做校验/发布接口，最后做多股道接触网与规模化。详见 §5、§6。

## 1. 需求拆解与判定口径

| 编号 | 需求 | 判定口径（本次评审采用） |
|------|------|--------------------------|
| R1 | 以中心线 GeoJSON 为基础 | 单条/多条 `LineString` 能直接驱动轨道与接触网 |
| R2 | 算法辅助生成基础参数化信息 | 算法输出的是**初始建议**，不是不可改的最终结果；建议与人工确认可区分 |
| R3 | 保存最基础的参数化数据 | 存下来的数据能重建几何，且**不包含可由输入推导的冗余**；字段的权威性明确 |
| R4 | 前端保存和手工调整 | 改一个对象只影响其依赖；删/增/改不破坏其它对象；重算不覆盖人工值 |
| R5 | 后端发布验证 | 有独立的校验入口，输出结构化、可定位到对象的报告 |
| R6 | 同时支持接触网与轨道 | 两专业能放在同一个项目里，空间与参数上互相对齐（竖向基准、里程、平面位置） |
| R7 | 路网尺度 | 多站场 + 区间 + 多锚段 + 关节，规模到数十公里/上百条边仍可用 |

R3/R4 是本次最关键的判据：**"能还原" ≠ "能编辑"**。现有实现满足前者，后者只满足一部分。

## 2. 现状：已有的三层能力

### 2.1 数据流

```
GeoJSON 中心线
  ├─ 轨道: CreateTrackFromGeoJSON ──────────────► Assembly(track)
  │         └（单条）轨道结构: rails + sleepers + ballast
  └─ 站场: ComputeYardLayout ─► YardLayout ─► CreateYardFromLayout ─► Assembly(yard)
  └─ 接触网: ParseAnchorSectionGeoJSON ─► ComputeAnchorSectionLayout ─► AnchorSectionLayout
                                                  └► CreateAnchorSectionFromLayout ─► Assembly(anchor_section)

Assembly ─► ExportParametric (JSON: 层级/name/location/color/Type/Params)
         ─► RebuildFromParametric (装配级 builder 优先, 叶片 builder 兜底)
```

### 2.2 层级

```
yard
├── track_i      (yard_track 装配级配方: 未裁剪中心线 + TrimS/TrimE + Props)
│   ├── rails_i  (yard_rails 叶片配方)
│   └── sleepers_i
├── turnout_i    (yard_turnout 配方: TurnoutParams + Position + Direction)
└── crossing_i   (yard_crossing 配方: DiamondParams + Position + Direction)

anchor_section
├── mast_i       (ocs_mast 配方 + Location; 角色 anchor/intermediate)
└── span_i       (ocs_span 装配级配方: 两索端点/弛度/吊弦 T 表/端锚下引)
    ├── cw_i / mw_i
    └── dropper_i_k
```

这套层级与 `docs/铁路装配体系评审.md` 的专业分解一致，是本模块最扎实的部分。

### 2.3 配方机制

- 叶片级 `RegisterParametricBuilder`：由参数回单个 `Shape`。
- 装配级 `RegisterAssemblyBuilder`：由参数整棵重建子装配，导出的 children 只作为前端编辑面，不参与重建（`assembly_parametric.go:161-171`）。
- `Assembly.Get` 支持顶层短名 / 路径 / 全树唯一深度名三级寻址（`assembly.go:356-420`）。
- 容器占位 vertex 已移入自身几何范围，避免污染 bbox。

### 2.4 已实测的验证

| 用例 | 覆盖 | 结果 |
|------|------|------|
| `TestYardParametricRoundTrip` | 站场 Export→Rebuild→再 Export，名称集合/JSON/bbox 一致（≤1mm） | 通过 |
| `TestAnchorParametricRoundTrip` | 锚段同上 | 通过 |
| `TestSpanAssemblyBuilderRebuild` / `TestSpanRecipeEditRebuild` | 单跨按配方重建；改弛度/吊弦表后几何跟随 | 通过 |

## 3. 与目标编辑器需求的逐项核对

### 3.1 基础数据是否"最小且可编辑"（R2/R3）

现状是**快照式布局**：算法把自己算出的密集中间结果物化进 JSON，重建时再读回来。逐字段看：

**`YardLayout`**

| 字段 | 实际性质 | 重建时是否读取 |
|------|----------|----------------|
| `Tracks[i].Centerline` | 输入（原始/已分段中心线） | 是 |
| `Tracks[i].TrimS/TrimE` | 算法派生（且语义不统一：`TrimS` 是"起点裁掉量"，`TrimE` 是"保留到的绝对弧长"；交叉分段后的股道又变成 0/全长） | 是 |
| `Tracks[i].Props` | 输入 | 是 |
| `Turnouts[i].Position/MainDir` | 算法派生（可手改） | 是 |
| `Turnouts[i].TurnoutNo/SwitchRailLength/LeadCurveRadius` | 派生 + 查表，可手改 | 是 |
| `Turnouts[i].FrogAngle` | 纯信息 | 否 |
| `Turnouts[i].EdgeIn/EdgeOut/EdgeDiv` | 拓扑引用，但**是数组下标** | 否 |
| `Crossings[i].Span` | 算法派生（让位半展长） | 仅生成阶段用，重建不读 |
| `Crossings[i].EdgeA/EdgeB` | 拓扑引用，数组下标 | 否 |
| `Warnings` | 自由文本 | — |

**`AnchorSectionLayout`**

| 字段 | 实际性质 | 重建时是否读取 |
|------|----------|----------------|
| `Spec.Centerline` | 输入副本 | **否**（重建只用 `Masts[]` 与 `Spec` 参数） |
| `Masts[i].Position/Direction/Stagger/MastHeight/ContactWireZ/MessengerWireZ/Role` | 输入 + 派生（可手改） | 是 |
| `Masts[i].ContactPoint/MessengerPoint` | 派生缓存 | **否**（`ocs_layout.go:372-375` 由柱位重算） |
| `Masts[i].Mileage/IsTensionMast` | 信息 / 派生 | `Mileage` 否；`IsTensionMast` 仅在无 `Role` 时兜底 |
| `Spans[i].Length` | 派生 | 否（吊弦数按两端点重算） |
| `Spans[i].ContactSag/MessengerSag` | **绝对弛度快照**（按标准跨距算，`ocs_layout.go:210-211`） | 是 |
| `Spans[i].Droppers[].T` | 输入/派生 | 是 |
| `Spans[i].Droppers[].Top/Bottom/Length` | 派生缓存 | **否** |
| `AuxWires[i].Points` | 派生折线（含 10m 密采样） | 是（重建直接放样，不再跟随柱位/线路编辑） |

由此得到三个结论：

1. **"保存最基础的参数化数据"没有做到**：布局里约一半字段是派生缓存，且这些缓存不在重建链路上（改了没效果）；真正的输入（哪条线路、哪段里程、布柱规则）反而没有被保存。`Spec.Centerline` 存了整条中心线却从不使用，是典型的冗余。
2. **字段权威性不可见**：前端拿到 JSON 无法区分"改这个有效 / 改这个无效"，必然踩坑。
3. **身份不稳定**：没有任何 ID。`track_0`/`mast_3`/`turnout_1` 都是下标生成的；前端删除/重排一个对象后，`EdgeIn/EdgeOut/EdgeDiv/EdgeA/EdgeB` 与跨的 `FromMast/ToMast` 会指向错误对象，且没有任何检测。

### 3.2 场景还原能力（R4）

分三种"还原"看：

| 场景 | 现状 | 结论 |
|------|------|------|
| 生成后原样保存，下次打开重建 | 布局 JSON / `ExportParametric` 都能确定性重建，实测 bbox ≤1mm | ✅ |
| 改参数（裁剪、道岔号数、弛度、吊弦表、柱位）后重建 | 已验证，几何跟随 | ✅ |
| 删/增/重排对象后再重建 | 无 ID、无引用校验；跨距必须手工补 `FromMast/ToMast`；股道拆分后源边身份丢失 | ⚠️ 需要人工维护一致性 |
| 改线路几何后重算 | 布局是快照，重算 = 重新导入 GeoJSON，**手工调整全部丢失** | ❌ |
| 改算法（布柱规则、道岔拟合）后升级场景 | 快照模型不吸收算法升级；没有 `algorithmVersion` | ❌ |

还有一个具体的一致性缺陷：**道岔/交叉与股道是彼此独立的快照**。`CreateYardFromLayout` 直接按 `Turnouts[i].Position` 放置，不与股道裁剪结果做校验。手工把股道 `TrimS` 拉长到覆盖道岔、或移动道岔位置，都会得到钢轨重叠/脱开，而系统不会报错。

接触网同理：`AuxWires[].Points` 和 `Spans[].ContactSag` 是快照，移动柱位后线索端点会跟随（由柱位重算），但附加导线折线与弛度不会跟随。

### 3.3 组装算法对真实站场/路网的适应性（R6/R7）

#### 3.3.1 拓扑识别覆盖

| 输入形态 | 现状 | 证据 |
|----------|------|------|
| 端点三叉（主线直线/近直线） | ✅ 识别为单开道岔 | `yard_layout.go:262` |
| 端点三叉（主线弯曲，道岔区内偏差 >100mm） | ❌ 直接跳过，只写一条中文 warning | `yard_layout.go:337-341`，`TestYardCurvedMainGuard` |
| 端点四叉（交叉渡线、复式交分、两线对接） | ❌ 一律不处理（`len(ends)!=3` 即 continue） | 同上 |
| 支线端点落在主线中部（GIS 常见"未打断"画法） | ❌ 不做端点-边吸附/打断，因此不识别道岔，钢轨直接重叠 | 代码中无 snap/split 逻辑 |
| 边中部相交（菱形交叉） | ✅ 支持锐角/直角 | `yard_layout.go:433-497`，`TestDiamondCrossingShallow`、`TestYardCrossingRightAngle` |
| 交叉点距任一端点 <2m | ❌ 视为道岔区丢弃 | `yard_layout.go:441` |
| 双开/三开/复式交分/交叉渡线 | ❌ 未实现（`AGENTS.md` 的 centerline_graph 方案只落地了单开+菱形） | — |
| 断头线、悬空端、重叠股道 | ❌ 无检测 | — |

#### 3.3.2 几何与参数覆盖

| 项 | 现状 | 影响 |
|----|------|------|
| 道岔轨距 | 硬编码 1435（`yard_layout.go:355`） | 1000mm 窄轨/宽轨项目静默错误 |
| 道岔钢轨断面 | 硬编码 60kg（`yard_layout.go:343`） | 43/50/75kg 股道与道岔断面不一致 |
| 菱形交叉轨距/断面 | 硬编码 1435/176/73/150（`yard_layout.go:486-489`） | 同上 |
| 道岔超高 | `TurnoutParams` 无超高字段 | 曲线站场道岔与股道轨面错位 |
| 道岔坡度 | 道岔是平面模型，只按节点 z 放置 | 坡道上岔区轨面与两端不连续 |
| 道岔类型 | 仅单开（左/右） | 站场咽喉的交叉渡线、复式交分无法表达 |
| 曲线道岔 | 不支持，且以"跳过"处理 | 正线曲线上的车站丢岔，拓扑断裂 |
| 股道道床 | `YardTrackLayout.Props` 有 `BallastTopWidth`，但 `buildYardTrackAssembly` 只生成 rails+sleepers | 站场显示无道床（`yard_layout.go:716-724`） |
| 扣件/基础 | 未进入布局生成 | 发布精度不足（可按需补） |
| 站场多股道接触网 | 布局生成器只支持单条中心线；软/硬横跨只有图元，没有布局 | 车站接触网无法生成（这是路网建模的高频场景） |
| 锚段关节网络 | 单关节 `CreateOcsJoint` 独立存在，未与锚段列表关联 | 无法表达"供电单元/分段绝缘器/关节链" |
| 布柱规则 | `CalcOcsSpanPositions` 全长等分，无避让（道岔区、桥、涵）、无不等跨调整 | 真实站场柱位几乎一定需要人工改 |
| 锚段长度/张力校核 | 无（如 15kN 下的最大锚段长度） | 发布校验缺失 |

#### 3.3.3 性能

- 菱形交叉识别是四重循环 `边×边×段×段`（`yard_layout.go:433-437`）。10 km 线路按 5m 采样、100 条边时约 `5e11` 次线段判交，不可用；必须有空间索引（网格/R-tree）。
- 多处 `polyArcLens` / `dirAtEnd` / `chordDir` / `frameAt` 在循环内重复计算弧长（每次 O(N)），节点多时退化为 `O(节点数×N)`。
- 重建是"整棵重来 + 全量三角化"，没有按对象增量重建或缓存；发布任务需要可控的分片与耗时预算。

### 3.4 前后端协同接口（R4/R7）

现有 Go 侧能提供的：JSON 布局、`ExportParametric`/`RebuildFromParametric`、`Get` 寻址、`SetLocation`/`Replace`（仅顶层，且内部是 remove+re-add，顺序会变）。

编辑器需要但缺失的：

| 能力 | 现状 |
|------|------|
| 稳定对象 ID | 无，全部按下标命名 |
| 局部更新（改一个属性） | 只能整对象重建或整文档重建 |
| 事务/撤销/批量编辑 | 无 |
| 结构化诊断（错误码 + 对象 ID + 位置） | 只有 `Warnings []string` |
| 数据 schema / 版本 / 迁移 | 无 `version` 字段；旧布局靠"缺 `Span` 就不分段"隐式兼容 |
| 项目级组合（轨道 + 接触网 + 地形/站房） | 无 `Project` 类型；两条线各自是根装配 |
| 算法建议 vs 人工确认 | 无区分，重算即覆盖 |
| 服务端 API 契约 | 只有库函数；没有"提交修订 → 校验 → 构建 → 产物"的任务接口 |

### 3.5 发布验证（R5）

- 铁路专业**没有** `Validate()`：`primitives_validate.go` 的规范值域校验只覆盖 GIM 变电/输电/电缆/矿山图元，`TurnoutParams` / `AnchorSectionSpec` / `YardLayout` 都没有。
- 站场/锚段构建只做"能不能生成"的检查，不检查：
  - 岔区与股道是否脱开/重叠；
  - 道岔出口与侧股起点的**位置/切向连续性**（当前侧股起点按投影裁剪 + 300mm 裕量，模型尾部是直线，而侧股可能是圆弧，存在小折角）；
  - 接触网与轨道限界、导高、拉出值是否合规；
  - 锚段长度、跨距、结构高度是否满足规范；
  - 几何自交/互穿（大装配 `IsValid` 代价过高，验收里直接跳过）。
- `Warnings` 不能机器消费，前端无法把"这里少了一个道岔"渲染成可处理的问题标记。

### 3.6 坐标、单位与竖向基准（R6）

| 项 | 现状 | 风险 |
|----|------|------|
| 长度单位 | 几何 mm，里程 m，GeoJSON m×`coordScale` | 前端/后端容易错位；字段级单位未声明 |
| 坐标系 | 假定 CGCS2000 投影，无 EPSG/投影参数 | 无法与 GIS/BIM 对齐 |
| 项目原点 | 无 | 大坐标（1e6~1e7mm）进入 three.js float32 会抖动 |
| 中心线 z 的含义 | 轨道：枕底/道床顶（钢轨另抬 200，`track_geojson.go:144-151`）；接触网：当作轨面（导高直接加在中心线 z 上） | **同一条线同时驱动两专业时，接触线实际导高少 376mm**（200 枕 + 176 轨） |
| 拉出值符号 | `staggerTable` 以"线路左侧为正"，但 `mastWirePoints` 在 `MastSide=-1` 时等效镜像 | 同一份之字表换侧后相位反转 |
| 里程 | 锚段只有柱位 `Mileage`（相对锚段起点），无绝对里程/断链 | 无法与线路资料对接 |

### 3.7 数据体积

- 每条股道在 `ExportParametric` 里存三份中心线：`yard_track`（未裁剪）+ `yard_rails`（裁剪后）+ `yard_sleepers`（裁剪后）。50 km、5m 采样的股道约 1 万点，单份 ~300KB，**单股道 ~0.9MB**；100 条股道就是 ~90MB 级。
- 锚段 `Spec.Centerline` 与 `AuxWires[].Points` 也是全量点列副本。
- 这些冗余对"还原"没有贡献（装配级 builder 会整棵重建，叶片配方实际不参与父节点重建）。

## 5. 目标设计建议

### 5.1 分层数据模型：输入 / 派生 / 覆盖

核心原则：**保存"决定几何的最小输入 + 人工覆盖"，派生数据只做缓存**。这与"算法辅助生成，前端手工调整"完全一致。

```
Project
├── meta            { id, name, crs: EPSG:4490, origin: [x,y,z], unit: {length:"mm", chainage:"m"}, version }
├── alignments[]    { id, geometry: LineString(3D, 轨面), chainage: {start, breaks[]}, superElevation[] }
├── railNetwork
│   ├── trackSegments[]  { id, alignmentId, s0, s1, params: TrackGeoProperties }
│   ├── junctions[]      { id, position, edges: [{alignmentId, s}], kind: turnout|crossing|unresolved, resolvedBy? }
│   ├── turnouts[]       { id, junctionId, hand, no, kind, params, overrides }
│   └── crossings[]      { id, junctionId, angle, a:{alignmentId,s}, b:{alignmentId,s}, kind }
└── ocsNetwork
    ├── anchorSections[] { id, alignmentId, s0, s1, spec, masts[]:{ id, s, side, role, type, overrides }, auxWires[] }
    ├── joints[]         { id, anchorA, anchorB, kind: insulated|nonInsulated, arms[] }
    └── switchMasts[]    { id, alignmentId, s, spec }
```

要点：

- **`Alignment` 是唯一中心线真源**。轨道段、道岔、锚段都只引用 `alignmentId + 里程区间`，不再复制点列。编辑线路 = 改一个对象，所有引用它的对象可重算。
- **`Junction` 是拓扑真源**。道岔/交叉是节点的解析结果；"未解析"也要显式保存（带原因码），供前端提示与人工指定，而不是丢进 `Warnings`。
- **`overrides` 只存人工改过的字段**（如 `turnoutNo`、`mast.s`、`trim`）。重算时 = 规则生成 + 覆盖合并，算法改进只影响未被覆盖的部分。
- 现有 `YardLayout` / `AnchorSectionLayout` 保留为**构建视图/缓存**（也给旧数据兼容），但不再作为编辑器保存格式。

### 5.2 管线

```
1. Extract   中心线 → 吸附/打断 → 图（节点/边，带稳定 ID）→ 节点分类 → 交叉检测
2. Resolve   规则生成参数建议（道岔号数/开向、导曲线半径、柱位、跨距、弛度）
             + 合并 overrides → 得到"已解析模型"
3. Build     输入模型 → Assembly（生成与重建共用同一套 builder，避免"两条路径分叉"）
4. Validate  结构/几何/规范三类校验 → 结构化报告（错误码 + 对象 ID + 位置 + 严重度）
5. Publish   通过校验后产出：模型 JSON（真源）、几何产物（glTF/IFC/STEP）、报告；按内容哈希幂等
```

`Build` 必须与 `Rebuild` 同构（`docs/铁路装配体系评审.md` 四·九 已经踩过"生成/重建两条路径外观不一致"的坑，应固化为纪律）。

### 5.3 编辑语义与一致性规则

| 编辑动作 | 应有行为 |
|----------|----------|
| 移动/改线路中心线 | 所有引用该 `alignmentId` 的轨道段、道岔位置、锚段柱位按里程重算；人工 `overrides` 保留 |
| 改股道 `s0/s1` | 只影响该股道；与道岔区重叠时给出校验错误 |
| 删股道 | 检查是否有道岔/交叉引用，阻止或级联删除并提示 |
| 增道岔 | 必须落在某 `junction` 上（或手工指定节点的边与里程），自动裁剪邻边 |
| 改道岔号数 | 只重算该道岔及其邻边裁剪，不动其它对象 |
| 移动支柱 | 重算相邻跨的端点、弛度（按 `sagRatio` 而非绝对值）、吊弦、附加导线 |
| 改锚段里程范围 | 重算柱位；保留人工钉住的柱位 |

三条硬规则：

1. **派生字段不回读**：布局里只保留输入与覆盖；派生在加载时重算。
2. **引用必须可校验**：`{alignmentId, s}` 或 `id`，禁止数组下标。
3. **重算幂等**：同一输入 + 同一 `algorithmVersion` 必须得到同一结果（现有代码已基本满足，需补版本号与缓存失效规则）。

### 5.4 组装算法能力补齐（按优先级）

1. **拓扑抽取**（必做）
   - 端点吸附到其它边的内部（容差按数据精度，如 50~200mm），打断成 T 型节点；
   - 节点分类：度 1（端头）、度 2（普通）、度 3（单开）、度 4（交叉/对接/双开）、度 ≥5（复式交分/咽喉）；
   - 全部节点产出 `Junction`（含未解析原因码），未解析不影响其余部分构建。
2. **曲线主线道岔**：道岔模型的基本轨沿 `Alignment` 弯曲（或增加 `curveOffset` 参数）；短期至少不"静默跳过"，而是生成占位节点 + 校验错误。
3. **道岔类型扩展**：按 `centerline_graph` 方案补双开/三开/交叉渡线/复式交分；先做"交叉渡线"（站场咽喉最高频）。
4. **参数继承**：道岔/交叉的轨距、钢轨断面、枕高、超高、坡度从股道/线路继承，缺省才查表。
5. **接触网布柱规则**：避让道岔区/桥隧/站台；允许不等跨；提供 `mastPinning`（人工钉住里程）。
6. **站场接触网**：`station_ocs` 布局（软横跨/硬横跨 + 多股道悬挂点 + 线岔），这是"路网 + 站场"必须补的一块。
7. **菱形交叉的性能与鲁棒性**：空间索引 + 按节点邻域检测，避免"近节点 2m 内丢弃"这种粗暴规则。

### 5.5 校验与发布接口

建议新增（Go 层，供后端服务直接调用）：

```go
type Issue struct {
    Code     string   `json:"code"`     // 如 RAIL.JUNCTION.UNRESOLVED
    Severity string   `json:"severity"` // error|warning|info
    ObjectID string   `json:"objectId"`
    At       [3]float64 `json:"at"`
    Message  string   `json:"message"`
    Hint     string   `json:"hint,omitempty"`
}

func ValidateProject(p *Project) []Issue
func BuildProject(p *Project) (*Assembly, []Issue, error)
func PublishProject(p *Project, opts PublishOptions) (*PublishResult, error)
```

校验分层：

| 层 | 内容 |
|----|------|
| 结构 | ID 唯一/引用完整；节点已解析或显式未解析；跨距索引有效；单位/CRS 完整 |
| 平面 | 岔区与股道不重叠、不脱开；道岔出口与邻边位置/切向连续（阈值如 5mm / 1mrad）；交叉区让位分段覆盖正确 |
| 竖向 | 统一轨面基准；道岔/股道/接触线 z 连续；导高、结构高度、拉出值范围 |
| 规范 | 道岔号数-半径匹配、最小曲线半径、锚段长度/张力、跨距上限、支柱限界 CX |
| 几何 | 抽样 `IsValid`（大装配按对象抽样，避免全量 `BRepCheck`）；必要时互穿检测（BVH/包围盒粗筛） |

发布产物建议：`model.json`（真源）+ `report.json`（校验）+ 几何（glTF 用于前端、IFC/STEP 用于交付）+ 内容哈希（幂等、可回溯）。

### 5.6 数据交换与版本

- 所有持久化 JSON 加 `schemaVersion` 与 `algorithmVersion`；提供 `Migrate(old) → new`。
- 旧 `YardLayout`/`AnchorSectionLayout` 作为"v0 快照格式"导入：把其中的派生值转成 `overrides`（保守策略，保证几何不变），后续编辑再逐步收敛到真源模型。
- 中心线存储：`Alignment` 一份；如需压缩，用增量编码/定点量化（如 0.1mm）+ 共享点列，禁止每个叶片复制。

## 6. 分阶段路线与验收标准

### P0（编辑器 MVP 的前置条件，建议 4~6 周）

1. 引入 `Project / Alignment / TrackSegment / Junction / Turnout / Crossing / AnchorSection / Mast` 与稳定 ID、schema 版本。
2. 布局字段权威性标注；派生字段不再回读、不再持久化。
3. 拓扑抽取：端点吸附/打断 + 节点分类 + 结构化 `Junction`（含未解析）。
4. 曲线主线道岔支持（或显式未解析 + 校验拦截）。
5. `ValidateProject` + `PublishProject` 骨架。

**验收**：构造一个"golden 路网"（建议 5km、含直线/曲线车站、≥20 组道岔、≥3 处菱形、≥5 个锚段），完成
① 导入 → 生成 → 保存 → 重开 → 重建，几何哈希一致；
② 修改一条中心线/一根柱位/一组道岔号数后，仅依赖对象变化，其余几何哈希不变；
③ `ValidateProject` 对每个 `Junction` 给出明确结论；
④ 计算与构建在设定预算内（如 5km/30 岔 < 10s）。

### P1（可用性，建议 4~6 周）

1. 道岔/交叉参数继承（轨距/断面/枕高/超高/坡度）；站场股道补道床。
2. 站场多股道接触网（软/硬横跨、线岔、悬挂点表）。
3. 多锚段 + 关节网络容器；锚段长度/张力/跨距校验。
4. 空间索引 + 弧长缓存 + 增量重建；中心线去重。
5. 统一竖向基准（GeoJSON z = 轨面），两专业组合场景对齐。

**验收**：同一 golden 路网叠加接触网，站场场景可生成横跨与悬挂；`ValidateProject` 能报出导高/限界/锚段超限；JSON 体积下降 ≥50%。

### P2（发布与规模化，建议持续）

1. IFC/glTF 产物与 LOD；发布任务队列、幂等、审计。
2. 断链/绝对里程；与外部线路资料对齐。
3. 道岔/支柱装置内部零件级编辑（可选）。
4. 前端事务/撤销/冲突检测（按对象 ID 的 patch 协议）。

## 7. 风险与假设

- **OCCT 校验代价**：大装配 `BRepCheck_Analyzer` 十分钟级并持有 `topo_glock`。发布校验必须分对象、限时、可取消，不能照搬验收里的全量 `IsValid`。
- **WASM 与 Go 语义差异**：文档已记录"退化链在 WASM 抛异常 / Go 返回几何"的分叉；编辑器若在浏览器侧预览，需要与后端一致的失败语义（至少一致的错误码）。
- **旧数据兼容**：现有布局 JSON 已被验收与测试固化；迁移必须保持几何等价，建议以"导入即转为 v1"的方式落地，不保留双写。
- **假设**：GeoJSON 中心线精度足以支撑道岔识别（米级坐标 + 亚米级拟合）；若上游是 1:2000 地形图数字化线，需先做曲线拟合/平滑，否则号数拟合会抖动。
- **未验证项**：本次未跑全量验收（耗时 ~40min），69/69 的结果来自仓库内 `acceptance/report.md`；P0/P1 的工期为经验估计，需结合团队规模复核。
